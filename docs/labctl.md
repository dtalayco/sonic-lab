# labctl

Draft specification. `labctl` is the main coordination tool for running lab
instances, and the control mechanism for lab tests (see
[Testing](testing.md)). Nothing here is implemented yet.

## 1. Concepts

**Lab (lab instance):** the unit of managing a system simulation. As a rule,
if things talk to each other, they are in the same lab, although a single
lab may be partitioned into disconnected domains.

**Topology:** the simulated devices in a lab and the links between them.

**Topology shorthand:** a name for a common pattern: spine-leaf, ring or
mesh. These are conveniences. Any topology can be described, and a shorthand
expands to the same topology description a user could write by hand.

**Device:** a simulated element of the topology, identified by a name unique
within the lab. Every device has a *type*, currently `switch` or `host`, and
more types can be added. A device is not the same as a container: a SONiC
switch today is two containers, a backing container that holds the network
namespace and the SONiC container that shares it.

**Port:** a named attachment point on a device, such as `spine1:Ethernet0`.

**Link:** a point-to-point connection between two ports. Links are native
Ethernet and are effectively hardwires between containers, so containers can
emulate any communications protocol on top of them as long as basic Ethernet
framing is used.

**Domain:** a set of devices connected to each other by links. A lab has one
or more domains, and no links exist between labs.

**Profile:** a named set of configuration applied across a lab, such as an L2
or L3 profile (see section 5 of
[Use Cases and Direction](use-cases-and-direction.md)).

**Machine:** the computer running the labs. "Host" is reserved for the
simulated device type, since the existing docs and tools already use it that
way.

**Lab directory:** the working directory that defines a lab (section 3).

**Repo:** a sonic-lab repository checkout, used for its tools and resources.

**Flow:** a sequence of `labctl` steps, possibly mixed with external
operations. A flow may be open ended. A test case is a flow that always
terminates with a status (see [Testing](testing.md)).

## 2. Existing components

**tgen** maps high-level topology descriptions to the docker compose files
and supporting files needed to run a configuration.

**webmesh** is a daemon, run as a container, that acts as the simulation
patch panel, allowing links between containers to be added or removed.

There is one webmesh per user and machine instance. We assume one user on a
machine, so this reduces to one webmesh per machine, shared by every lab on
it. Connecting multiple machines into one lab is an unplanned roadmap
feature.

Webmesh is a separate service that operates asynchronously from everything
else. It is not part of any lab, and its lifetime is independent of theirs.
A lab declares the links it wants, identified by lab instance, and webmesh
reconciles them whenever the devices are present. Multiple labs running at
once is the design target.

## 3. Deployment model

A lab is determined by a directory, which holds:

- Any config files, state files and space needed by the lab's components.
- A docker compose file describing the containers that make up the lab.
- A reference to a repo, used to access the necessary tools (for example
  webmesh and tgen). This is a shortcut to managing a venv for the lab.

```
dc1/
├── lab.yml               # Lab definition: the input
├── topology.yml          # Topology description: input or expanded shorthand
├── docker-compose.yml    # Generated by tgen
├── .env                  # Generated; lets docker compose run here directly
├── frr/ ...              # Other generated config and scripts
├── state/                # labctl and component state
└── logs/                 # Collected on stop or failure
```

```yaml
# lab.yml
version: 1
name: dc1                 # Defaults to the directory name
repo: /home/dan/work/sonic-lab
topology: topology.yml
profiles:
  l2: trunk
  l3: none
```

Rules:

- **Name:** the lab name is unique on the machine and is the compose project
  name. It prefixes every container name, so labs can coexist.
- **Repo:** taken from `--repo`, then `SONIC_LAB_REPO`, and recorded in
  `lab.yml` on first start. Later commands use the recorded value.
- **Portability:** the lab directory can live anywhere the Docker daemon can
  bind mount from. On macOS, that means a path shared with the Colima VM.
- **Generated files:** generated on first start and left alone after that,
  so hand edits survive until `start --regenerate`.
- **Compose remains usable:** `docker compose ps` and `docker compose logs`
  work in the lab directory. `labctl` does not hide Docker.
- **Live state:** Docker and webmesh are the source of truth. `status` asks
  them rather than trusting a state file.

## 4. Command line interface

### 4.1 Conventions

These apply to every command:

| Flag | Meaning |
|---|---|
| `-C, --dir DIR` | Lab directory (default: `LABCTL_DIR`, then the current directory) |
| `-o, --output FORMAT` | `text` (default) or `json` |
| `--output-file PATH` | Write the result to a file instead of stdout |
| `-q, --quiet` | Errors only |
| `-v, --verbose` | More diagnostics; repeatable |
| `--timeout DURATION` | Limit for the whole command, such as `10m` |
| `-h, --help` | Help |
| `--version` | Version of `labctl` |

Behavior:

- The result goes to stdout. Progress and diagnostics go to stderr, so
  output can always be piped.
- Color and progress displays are off when the stream is not a terminal.
- JSON output is one document with a `version` field, and its fields are a
  stable interface.
- No command prompts for input. Every wait has a timeout.
- `start` and `stop` are idempotent: repeating one that has already happened
  succeeds without doing anything.
- Commands take the form `labctl <verb>` for the lab lifecycle and
  `labctl <noun> <verb>` for operations on parts of a lab.

Exit codes:

| Code | Meaning |
|---|---|
| 0 | Success |
| 1 | Negative result: the command ran, and the answer is no (lab not ready) |
| 2 | Usage error |
| 3 | Operational error: the command could not do its job (Docker down, build failed) |
| 4 | Timeout |

### 4.2 `labctl start`

Start the lab in the lab directory, creating the directory and its
definition if needed.

```
labctl start [-t, --topology FILE|SHORTHAND] [--repo DIR]
             [--l2 PROFILE] [--l3 PROFILE]
             [--wait-for LEVEL] [--regenerate]
```

```sh
labctl -C ~/labs/dc1 start -t spine-leaf:2x4
labctl -C ~/labs/r4 start -t ring:4 --l3 none
labctl -C ~/labs/custom start -t ./my-topology.yml
labctl start                                       # Existing lab, in cwd
```

`--wait-for` selects the readiness level to wait for: `containers`, `wired`,
`ports` or `converged`. The default is `wired`.

Steps:

1. Read `lab.yml`, or create it from the flags.
2. Check prerequisites: Docker, Compose, the repo, name conflicts.
3. Ensure the webmesh service is running and compatible.
4. Generate the lab files with tgen if needed.
5. Build or pull images.
6. Declare the lab's links to webmesh.
7. Start the containers that links attach to (backing containers and
   hosts), and wait until webmesh reports the lab's links wired.
8. Start the remaining containers.
9. Wait for the requested readiness level.

If a step fails, `start` reports it, exits nonzero and leaves the lab as it
is for debugging. `labctl stop` cleans it up.

### 4.3 `labctl status`

Report the state of a lab, or with `--all`, of every lab on the machine.

```
labctl status [-a, --all]
```

```
$ labctl status
Lab:      dc1 (/home/dan/labs/dc1)
State:    ready
Devices:  6/6 running
Links:    8/8 wired
Ports:    16/16 up
```

```json
{
  "version": 1,
  "name": "dc1",
  "dir": "/home/dan/labs/dc1",
  "state": "ready",
  "devices": {"desired": 6, "running": 6},
  "links": {"desired": 8, "wired": 8},
  "ports": {"desired": 16, "up": 16}
}
```

Lab states are `stopped`, `starting`, `ready`, `degraded` and `failed`. The
command exits 0 for `ready` and 1 for any other state.

### 4.4 `labctl stop`

Stop the lab, remove its containers and remove its links from webmesh. The
lab directory stays, so `labctl start` brings the same lab back up. The
state inside the containers does not survive.

```
labctl stop [--purge] [--collect-logs]
```

`--purge` also removes the lab directory's generated files and state, leaving
only the inputs. Webmesh keeps running, since other labs may be using it.

### 4.5 Modify operations

Use cases will drive these, so they are not specified yet. Candidates:

| Use case | Likely operations |
|---|---|
| UC1 host-side protocol development | Exec into a device, attach a custom host image |
| UC2 L2, UC3 L3 | Apply a profile, change device config |
| UC4 test matrix | Run a flow or test set |
| UC5 failure and resilience | Link up and down, device restart, topology change |
| UC6 manual exploration | Exec, logs, capture on a link |
| UC7 regression | Readiness and level checks, log collection |

## 5. Implementation language: Go

`labctl` will be written in Go.

- **Fits the repo:** tgen, webmesh and webmeshctl are already Go, so this
  adds no toolchain, and `labctl` can reuse webmesh's API types.
- **Deployment:** a single static binary with no runtime or environment to
  manage, which suits a tool meant to live on the path independently of the
  repo.
- **Familiar interfaces:** Cobra provides short and long flags, nested
  commands, generated help and shell completion. It is what docker, kubectl
  and gh use, so the conventions in section 4.1 come naturally.
- **Production quality:** static types, and straightforward concurrency for
  polling many devices and enforcing timeouts.

The tradeoff is slower iteration than Python. Extensions need not be in Go:
`labctl foo` can run an executable called `labctl-foo` from the path, as git
and kubectl do, and JSON output gives those extensions a stable interface.

## 6. Changes needed in existing tools

tgen:

- Accept a topology file as input. Today it only takes flags, so the
  shorthands are the only topologies it can produce.
- Prefix container names with the lab name. They are fixed today, as are the
  `/var/run/redis-vs/<switch>` paths on the machine.
- Reference the repo through `.env` rather than `context: ..`, which removes
  the rule that a lab must be a direct child of the repo.
- Stop generating the webmesh service and the dependency on it.

webmesh:

- Add the lab instance to the device spec in its config. This is the main
  change. Pushing a topology then replaces only that lab's links, where
  today it replaces all of them, and links between labs can be refused.
- Report health per lab, separately from the health of the service. Today
  `healthy` covers everything in the daemon, and is false when no links are
  desired, which is the normal state of an idle service.
- Run standalone rather than from a lab's compose file, with topologies
  arriving through the API instead of a mounted file.
- Fix `PUT /v1/topology`, which does not accept the topology file format
  (the file loader does), and add `GET /v1/topology`.
- Survive restarts. A shared daemon makes issue #32, and SONiC's failure to
  recover replaced veths, a problem for every lab on the machine.

## 7. Milestones

Multiple labs running at once is required for version 1 of `labctl`, but the
work can be separated:

- **webmesh config change:** adding the lab instance to the device spec can
  be done early and independently, with labs that omit it behaving as they
  do today.
- **labctl:** `start`, `status` and `stop` can be developed against one lab
  at a time, keeping the interface unchanged.
- **Version 1:** webmesh runs as a separate service, and multiple labs run
  at once.

## 8. Open questions

- **Versions on a shared machine:** each lab references a repo, but webmesh
  is shared and image tags such as `sonic-lab/webmesh:latest` are global to
  the machine. Two labs on different checkouts can conflict. Options are
  version-tagged images, or one repo per machine.
- **Managing webmesh:** as a separate service, what starts, stops and
  upgrades it? `start` could bring it up if it is absent, with something
  like `labctl webmesh status|stop`, refusing while labs are running.
- **Readiness default:** `wired` returns quickly, but `converged` is what a
  user usually means. It also depends on the L3 profile.
- **Topology format:** can today's `topology.yml` be extended to describe all
  devices, including hosts, as the one input format?
- **Separate create step:** `start` creates a lab implicitly. Is a
  `labctl init` useful for editing the files before the first start?
